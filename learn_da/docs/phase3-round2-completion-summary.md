## 四、默认顺学建议的具体规则

### 4.1 规则逻辑

```
1. 如果当前有课程且已完成：
   → 推荐其 recommended_next 中第一个未完成课程
   → 理由："你已完成《当前课》，建议继续学习下一课"
   → 优先级：4（高）
   → 按钮："继续学习"

2. 如果当前有课程但未完成：
   → 返回 None（不推荐新课程）
   → 让用户先完成当前课

3. 否则找第一个未完成的课程（按 order 排序）：
   a. 如果是第一课：
      → 理由："推荐从第一课开始学习"
      → 优先级：3
      → 按钮："开始学习"
   
   b. 如果不是第一课：
      → 理由："推荐继续学习《课程名》"
      → 优先级：2
      → 按钮："开始学习"

4. 如果全部完成：
   → 返回 None
```

### 4.2 规则特点

- **简单稳定**: 只依赖课程元数据和完成列表，不依赖复杂分析
- **可解释**: 每个建议都有明确理由
- **尊重进度**: 当前课未完成时不推荐新课
- **优先级清晰**: 完成当前课后的后继 > 第一课 > 其他未完成课程

### 4.3 测试验证

```
✓ 场景1: 新用户 → polars-basics (第一课)
✓ 场景2: 完成第一课 → duckdb-analytics (后继课程)
✓ 场景3: 完成第一课且标记为当前 → duckdb-analytics (优先级4)
✓ 场景4: 当前课未完成 → None (正确，先完成当前课)
✓ 场景5: 完成多门课程 → polars-expressions (顺序推进)
```

## 五、页面接入说明

### 5.1 Dashboard 接入

**位置**: 概览 tab，统计卡片和连续学习卡片之后

**展示内容**:
- 💡 图标 + "下一步学习建议"标题
- 目标课程标题（大字）
- 推荐理由（小字）
- 行动按钮（蓝色，显示 actionLabel）

**兜底策略**:
- 有新建议：优先展示新建议卡片
- 无新建议但有旧推荐：展示旧推荐课程卡片
- 都没有：不显示任何卡片

**实现方式**:
```vue
<div v-if="recommendation?.primary" class="bg-gradient-to-r from-blue-50 to-indigo-50 ...">
  <!-- 新建议卡片 -->
</div>
<div v-else-if="recommended?.recommended" class="bg-gradient-to-r from-blue-50 to-indigo-50 ...">
  <!-- 旧推荐卡片（兜底） -->
</div>
```

### 5.2 Learning 页接入

**位置**: 路径介绍卡片之后，筛选栏之前

**展示内容**:
- 💡 图标 + "下一步学习建议"小标题
- 目标课程标题（粗体）
- 推荐理由（小字）
- 行动按钮（蓝色，显示 actionLabel）

**兜底策略**:
- 有新建议：展示新建议区块
- 无新建议但有上次访问：展示"继续上次学习"区块
- 都没有：不显示任何区块

**与原有功能并存**:
- 不影响路径浏览
- 不影响筛选功能
- 不影响课程列表展示

**实现方式**:
```vue
<div v-if="recommendation?.primary" class="mb-6 ...">
  <!-- 新建议区块 -->
</div>
<div v-else-if="activeCategory === 'all' && lastVisitedSlug" class="mb-6 ...">
  <!-- 继续学习区块（兜底） -->
</div>
```

### 5.3 LessonDetail 页接入

**位置**: 课程正文底部，示例代码卡片之前

**展示内容**:
- 💡 图标 + "学完本课后的建议"小标题
- 目标课程标题（大字）
- 推荐理由（小字）
- 行动按钮（蓝色，显示 actionLabel）

**兜底策略**:
- 有新建议：展示建议区块
- 无新建议：不显示（用户可通过原有的 prev/next 导航）

**避免断流**:
- 学完一课后立即看到下一步
- 明确的行动入口
- 不依赖用户主动寻找

**实现方式**:
```vue
<div v-if="recommendation?.primary" class="mt-12 p-6 ...">
  <!-- 学后建议区块 -->
</div>
```

## 六、用户拿不到建议的情况及兜底

### 6.1 无建议的场景

| 场景 | 原因 | 兜底方案 |
|------|------|----------|
| 当前课未完成 | 规则设计：先完成当前课 | 不显示建议，让用户专注当前课 |
| 全部课程已完成 | 没有未完成课程 | Dashboard/Learning 显示旧推荐（如有），LessonDetail 不显示 |
| API 请求失败 | 网络或服务异常 | 静默失败，显示兜底内容 |
| 元数据缺失 | 课程配置问题 | 推断逻辑兜底 |

### 6.2 兜底策略

**Dashboard**:
1. 优先：新建议卡片
2. 兜底1：旧推荐课程卡片（`recommended?.recommended`）
3. 兜底2：不显示任何卡片

**Learning 页**:
1. 优先：新建议区块
2. 兜底1：继续上次学习区块（`lastVisitedSlug`）
3. 兜底2：不显示任何区块（用户可浏览课程列表）

**LessonDetail 页**:
1. 优先：新建议区块
2. 兜底：不显示（用户可用原有 prev/next 导航）

### 6.3 错误处理

所有 API 请求都使用 `.catch(() => null)` 静默处理：
- 不阻塞页面加载
- 不显示错误提示
- 优雅降级到兜底方案

## 八、关键设计决策

### 8.1 为什么当前课未完成时不推荐新课？

**原因**:
- 避免用户分心，专注完成当前课
- 防止建议系统鼓励"跳学"行为
- 保持学习路径的连贯性

**实现**:
```python
if current_lesson_slug in completed_lessons:
    # 已完成，推荐后继
else:
    # 未完成，返回 None
    return None
```

### 8.2 为什么优先级是 4 > 3 > 2？

**优先级策略**:
- **4（最高）**: 完成当前课后的后继课程（用户有明确上下文）
- **3**: 第一课（新用户的最佳起点）
- **2**: 其他未完成课程（顺序推进）

**目的**: 让前端可根据优先级调整展示样式或排序

### 8.3 为什么不在本轮做回补建议？

**原因**:
- 回补建议需要 analytics 数据支持
- 需要定义"卡住"的明确规则
- 需要验证回补课程的有效性
- 本轮重点是"稳定跑通默认顺学"

**下一轮计划**:
- 先跑通顺学建议，验证用户反馈
- 再基于真实数据设计回补规则
- 避免过早优化

### 8.4 为什么建议区块放在课程正文底部？

**原因**:
- 用户学完正文后自然看到
- 不干扰课程内容阅读
- 提供明确的"下一步"行动
- 避免用户学完后不知道做什么

**替代方案**:
- 放在顶部：干扰内容阅读
- 放在侧边栏：移动端体验差
- 不放：用户断流
